## 1. Intro
- 내가 신입으로서 다른 생각을 가졌을때
    - 다른 관점(나의)의 가치를 과소평가하지말자
    - 말이 안 되는 것을 발견하면 설명을 요청하라 -> 질문이 배우려는 욕구라면 대부분 긍정적으로 토론한다.
- 성급하게 결정하지 말자
    - 고객의 요청 뒤에 있는 이유의 근본을 찾자
    - 연속된 왜? 질문
- 컴파일러가 아닌 사람을 위해 최적화하자
- 멘토를 찾자
    - 조직의 선임에게 정중한 커피챗
    - 그들의 경험, 배운 것, 더 일찍 배웠으면 좋았을 것, 내가 배워야 한다고 생각하는 것

## 2. Reading Code
- “Code is read much more often than it is written”
- 현업 엔지니어로서 대부분의 시간은 레거시 코드를 다룰것이다.
- 레거시 코드를 다룰때 4가지 어려운 점
    - 해결하려는 비즈니스 문제를 이해해야 한다.
    - 먼저 작업한 개발자의 시각에서 봐야 한다.
        - 개발자마나 나름의 습관, 문제 해결 방식이 있다.
    - 기존 코드가 적절한 추상화 수준을 갖추지 못했을수도
    - 고고학자처럼, 오래된 기술과 안티패턴으로 간주될 수 있는 접근법을 층층이 벗겨내야 할지도
        - 시간에 따라 언어와 “올바른” 방법은 진화한다. -> 작성된 시점의 관점에서 봐야 한다.
- 문서와 시간을 보내자
    - 문서가 최신이 아니면 배우면서 업데이트하는걸 고려하자 -> 내 이해뿐만 아니라 미래 개발자에 도움이 된다.
    - 문서에 있으면 좋은 내용
        - 서비스가 하는 일
        - 어떻게 작동하는지
        - 뭐를 의존하는지
        - 어떻게 실행하는지
- 코드 구조를 분석하자
    - 직감적으로 브레이크포인트 설정하자 -> 틀리면 다시 찍어보자
    - 코드가 이름이 암시하는대로 동작한다 가정하지 말자 <- 코드가 발전하면서 더 이상 메서드 이름이 현실을 반영하지 않을 수 있다.
    - git blame으로 작성자를 보자 -> 누구한테 질문할 지 알 수 있다.
    - Umbrello, Doxygen 같은 도구로 코드베이스에서 다이어그램을 추출하자
        - 코드 커밋마다 최신 다이어그램 생성을 빌드 파이프라인에 추가해보는것도 고려
    - IDE의 show hierarchy 기능으로 역할 파악
- 엣지 케이스를 찾아보자
    - 다시 발생하지 않도록 테스트가 작성된 경우가 많다.

## 3. Writing Code
- 코딩은 의사소통이다 -> 컴파일러뿐만 아니라 사람이 이해할 수 있도록 집중하라 -> 의도가 명확해야 한다
- 바퀴 재발명 ㄴ
- 어제의 모범 사례는 내일의 안티패턴인 경우가 많다. -> 현재의 코드에 계속 의문을 가져라
- 메트릭은 코드베이스에 대한 통찰을 줄 수 있다.
    - 순환 복잡도가 높을수록 리팩토링이 필요할 가능성
    - SonarQube, CodeScene같은 걸로 통찰을 찾자
    - 차근차근 추가하자 팀원과 천천히
    - 지표가 남용되는것도 언제나 조심
- Zeroth Law - 높은 응집도 낮은 결합도 -> 유지보수 좋을 확률
- 상속보단 컴포지션
- 짧은 메서드 선호
- 주석은 꼭 필요할때 작성하자
- 새로운 언어를 탐구하고 배우자
    - 어떤 사람(실용주의 프로그래머 저자)은 1~2년에 새로 언어 배우는걸 권장
    - 새로운 패러다임의 언어를 배워보라 자바 개발자면 동적 언어나 함수형
    - 경력 초기면 매일 사용하는 언어와 프레임워크에 깊이 파고드는데 집중하자
